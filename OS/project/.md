## 📆 12–14 Week Plan (Flexible Semester)

### **Phase 1 — System Programming Core (Weeks 1–3)**

**Goal:** Master process control, file I/O, and IPC (Inter-Process Communication).

#### 🧩 Tasks

1. **File Management Module**

   * Build a C program that opens, reads, writes, and locks files safely.
   * Implement your own simple “log writer” with buffered writes.
   * Learn about file descriptors, offsets, and race conditions.

2. **Process and Fork Experiments**

   * Write small programs using `fork()`, `exec()`, and `wait()`.
   * Observe shared file offsets and conflicts in reads/writes.

3. **Pipes & Shared Memory**

   * Implement a **pipe-based chat** between parent and child.
   * Then switch to **System V shared memory** for faster transfer.
   * (Mini project name: `local_comm.c`)

🧠 Outcome: You can move data between processes efficiently — base for your broker queues.

---

### **Phase 2 — Concurrency & Synchronization (Weeks 4–5)**

**Goal:** Handle multiple producers/consumers safely.

#### 🧩 Tasks

1. **Threaded Queue System**

   * Use `pthread` to simulate producers and consumers.
   * Protect the queue using `pthread_mutex` + `sem_t` semaphores.

2. **Implement a Job Queue**

   * Each job = struct { id, payload, timestamp }
   * Demonstrate enqueue/dequeue with thread-safe access.

3. **Add Persistence**

   * Log every job to a file (`queue.log`).
   * On restart, reload previous jobs (like Redis AOF).

🧠 Outcome: You’ll have your first “mini message queue.”

---

### **Phase 3 — Networking Basics (Weeks 6–7)**

**Goal:** Build communication between nodes using sockets.

#### 🧩 Tasks

1. **TCP Server/Client**

   * Write a socket-based client/server app.
   * Exchange simple text messages (“publish/subscribe”).

2. **Non-blocking I/O (select/poll)**

   * Make the server handle multiple clients simultaneously.

3. **Serialize Messages**

   * Design a small message format:

     ```c
     struct Message {
       char topic[32];
       char payload[256];
     };
     ```

🧠 Outcome: Local message broker prototype that accepts messages from multiple clients.

---

### **Phase 4 — Core Broker Logic (Weeks 8–9)**

**Goal:** Combine file storage + threads + sockets = working broker.

#### 🧩 Tasks

1. **Broker Core**

   * Create `EdgeMQ` server that:

     * Accepts TCP clients
     * Handles PUB/SUB commands
     * Uses threads for message dispatch

2. **Topic Routing**

   * Maintain a simple in-memory topic table (like a map)

     ```
     topic → list of client sockets
     ```
   * Broadcast messages to subscribed clients.

3. **Offline Queue (Local Persistence)**

   * When client disconnects, store undelivered messages in a file.
   * On reconnect, replay them (like MQTT QoS).

🧠 Outcome: Local broker running on Linux terminal — multiple clients publish/subscribe!

---

### **Phase 5 — Cloud Layer (Weeks 10–11)**

**Goal:** Bring in your cloud knowledge.

#### 🧩 Tasks

1. **Cloud Sync API (Node.js / Express)**

   * REST endpoint: `/sync` that receives messages from edge brokers.
   * Store them in MongoDB or Redis.
   * Send back acknowledgments.

2. **Edge-to-Cloud Sync**

   * Extend your C broker to:

     * Detect “internet available”
     * POST stored messages to your cloud API
     * Clear local cache on success

3. **Simple Web Dashboard**

   * Show:

     * Connected brokers
     * Messages per topic
     * Sync status

🧠 Outcome: Distributed hybrid broker — **works offline and syncs online**.

---

### **Phase 6 — Packaging, Optimization, and Open Source (Weeks 12–14)**

**Goal:** Make it real-world and publishable.

#### 🧩 Tasks

1. **Add Config File Support**

   * Read from `edgemq.conf` (like port, max queue size, sync URL).

2. **Dockerize the Broker**

   * Create a Dockerfile for your C app and cloud service.

3. **GitHub + Docs**

   * Add:

     * README (architecture + usage)
     * LICENSE (MIT or Apache)
     * CONTRIBUTING.md
   * Use GitHub Actions for automatic build/test.

4. **(Optional) CLI Client**

   * Build a small `edgemq-cli` in C or Node to interact with broker.

🧠 Outcome: You’ll have your own **open-source, C-based message broker** with cloud sync.
